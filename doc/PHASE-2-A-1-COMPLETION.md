## What shipped

1. **`DebianBuildReportV1`** in
   `bins/ironmaint-debian-tool/src/report.rs` — a new
   `schemars::JsonSchema` + `Serialize`/`Deserialize`
   struct next to the five existing Debian reports. The
   fields follow the §82–96 spec: `provenance`
   (`{ candidate_fingerprint, commit, tree_sha }`),
   `source_package` (`{ name, version }`), `target`
   (`{ suite, arch }`, matching `BuildTarget`'s shape),
   `producer` (`{ name, version, build_environment_id }`),
   `started_at` / `finished_at` (RFC 3339 UTC),
   `exit_code`, `outcome`, `references: Vec<ArtifactRef>`,
   `diagnostics: Vec<Diagnostic>` (reuses the existing
   `Diagnostic { code, message, path }` from
   `bins/ironmaint-debian-tool/src/report.rs:62`).
   Constants: `BUILD_REPORT_KIND = "debian.build_report_v1"`,
   `BUILD_REPORT_SCHEMA_VERSION = 1`. The committed
   `schemas/DebianBuildReportV1.json` is regenerated by
   `cargo run -p xtask --locked -- verify-schemas --write`
   and matches the live schema byte-for-byte
   (`verify-schemas` reports `14 type(s), no drift`).

2. **`BuildOutcome` enum** (in
   `bins/ironmaint-debian-tool/src/report.rs`): 4
   wire-level variants — `Pass`, `PackageBuildFailed`,
   `InfrastructureFailed`, `Unknown(String)`. The other
   two "missing tool" and "malformed stdout" cases are
   detected from the `ExecutionRecord` shape inside the
   normalizer (empty stdout + exit 127, or JSON parse
   failure) rather than represented on the wire — the
   tool that produced `BuildOutcome::InfrastructureFailed`
   had to *succeed enough* to emit a valid report.

3. **`DebianBuildReportNormalizer`** in
   `bins/ironmaint-debian-tool/src/normalizer.rs`,
   modelled on the existing `DebianBtsSnapshotNormalizer`.
   Maps:

   | Report / record shape | Normalizer output |
   |---|---|
   | `BuildOutcome::Pass` | `Ok(NormalizedResult { EvidenceStatus::Pass, … })` |
   | `BuildOutcome::PackageBuildFailed` | `Ok(NormalizedResult { EvidenceStatus::Fail, observations: <diagnostics> })` |
   | `BuildOutcome::InfrastructureFailed` | `Err(NormalizationError::Unclassifiable("debian.build.sbuild: infrastructure failure"))` |
   | `BuildOutcome::Unknown(reason)` | `Err(NormalizationError::Unclassifiable("debian.build.sbuild: unknown failure mode: <reason>"))` |
   | stdout empty + exit 127 | `Err(NormalizationError::Unclassifiable("debian.build.sbuild: missing tool …"))` |
   | stdout not parseable | `Err(NormalizationError::Malformed("debian.build.sbuild: <serde error>"))` |

   The `Unclassifiable` cases map through
   `ExecutorError::InfrastructureFailed` to
   `GateStatus::Blocked`; `Malformed` maps to
   `Outcome::Fail` (a defect, not an outage). The
   `Unknown(reason)` arm is the §96
   "unknown failure modes must not be silently classified
   as package defects" guard.

4. **`ironmaint-debian-tool build` subcommand** in
   `bins/ironmaint-debian-tool/src/main.rs`:
   `Sub::Build` clap variant + `run_build_cmd()`. The
   2A.1 body is a stub that:
   - reads (and discards) the v3 candidate input from
     stdin so the executor's `JsonStdin` wiring is
     exercised end-to-end,
   - touches each of the seven `BUILD_*` env vars
     (`BUILD_INPUT_DIR`, `BUILD_OUTPUT_DIR`,
     `BUILD_TARGET_SUITE`, `BUILD_TARGET_ARCH`,
     `BUILD_FINGERPRINT`, `BUILD_COMMIT`,
     `BUILD_TREE_SHA`) so the contract 2A.2 will populate
     per-call is exercised even though the stub does not
     use the values,
   - emits a hard-coded
     `DebianBuildReportV1 { outcome: Pass, .. }`. 2A.3
     replaces this body with a real `sbuild` invocation;
     the subcommand literal `"build"` and the env-var
     contract are what 2A.3 must honour.

5. **`register_debian_tools` helper** in
   `bins/ironmaintd/src/tools.rs` (new module), exposed
   via `bins/ironmaintd/src/lib.rs:29`
   (`pub use tools::register_debian_tools;`). The helper
   registers all six real Debian tools
   (`debian.inspect.source_preparation`,
   `debian.inspect.source_analysis`,
   `debian.inspect.maintenance_context`,
   `debian.policy.delta_review`,
   `debian.issue.bts_snapshot`, and 2A.1's new
   `debian.build.sbuild`). Each registration is a
   private `register_debian_*` function so the new build
   registration is visible in the same place as the
   existing five. The build registration uses the
   conservative `debian_limits_build()` shape: 30-minute
   timeout, 8 MiB stdout, 8 MiB stderr. 2A.3 tunes
   these against the `pinned-real` fixture once the real
   sbuild invocation is in place.
   **`bins/ironmaintd/src/main.rs:217-241`** now calls
   the helper instead of carrying five in-line
   `ToolDefinitionRecord::new(...)` blocks at the bottom
   of the startup sequence. The change is invisible at
   runtime (same six tools in the same registry) but
   makes the new registration a single line in the same
   file as the existing five, and makes the helper
   callable from a hermetic test.

6. **Hermetic tests**, six in total:

   - `bins/ironmaint-debian-tool/tests/build_report.rs`
     (5 tests, RED in the prior commit) —
     `build_pass_report_normalises_to_pass`,
     `build_package_fail_report_normalises_to_fail`,
     `build_infra_fail_report_normalises_to_unclassifiable`,
     `build_malformed_stdout_normalises_to_malformed`,
     `build_missing_tool_normalises_to_unclassifiable`.
     Each constructs a canned `ExecutionRecord` and calls

   - `bins/ironmaintd/tests/build_tool_registration.rs`

     `build_sbuild_tool_is_registered`. Calls
     `ironmaintd::register_debian_tools(&mut registry,

     `ToolRegistry::get(&ToolCapabilityKey::new("debian.build.sbuild").unwrap()).is_some()`.

   All 6 tests pass GREEN in this commit.

7. **S3 capability-inventory test wired to the daemon's
   real tool set.** `daemon_registered_tools()` in
   `crates/ironmaint-adapter-api/tests/capability_inventory.rs`

   `ironmaintd::register_debian_tools(&mut registry, &debian_tool_bin, None)`

## Deviations from the design doc

The 2A.1 design doc (`doc/PHASE-2-A-1.md`) outlined
five decisions and an allowlist of small assumptions.
Most landed as designed. The two that changed in
implementation:

1. **`BuildOutcome` is 4 wire-level variants + 2
   normalizer-only cases, not 6 wire-level variants.**
   The design doc had a misleading "6-variant
   BuildOutcome" shape; the implementation cleanly
   separates the on-the-wire enum (4 variants) from
   the shapes the normalizer detects from the
   `ExecutionRecord` (empty stdout + exit 127, JSON
   parse failure). The wire format is what 2A.3 has
   to honour; the normalizer-only cases are the
   tool-not-found / tool-malformed guards and never
   appear on the wire. The amended `BuildOutcome` is
   in `bins/ironmaint-debian-tool/src/report.rs:1459`.

2. **The daemon's tool registration is extracted into
   `ironmaintd::register_debian_tools`, not left in
   place at `bins/ironmaintd/src/main.rs:217-388`.**
   The design doc had said the in-line form was
   "deliberately left in place" for symmetry with the
   1C.x / 1D.2 / 1E.2 PRs. The implementation
   extract collapses the five in-line
   `ToolDefinitionRecord::new(...)` blocks into a
   single helper, which is the only way the new
   `debian.build.sbuild` registration can be visible
   in the same place as the existing five *and* the
   helper can be called from a hermetic test
   (`bins/ironmaintd/tests/build_tool_registration.rs`).
   The runtime behaviour is identical (same six
   `ToolDefinition` records in the same `ToolRegistry`
   with the same normalizers); the change is
   structural. The five S3 test entries that the
   existing five keys enable (`debian.inspect.*` /
   `debian.policy.delta_review` /
   `debian.issue.bts_snapshot`) are now also covered
   by `daemon_registered_tools()` — a pre-existing
   gap in the test, recorded as **D-27** and closed
   by 2A.1.
